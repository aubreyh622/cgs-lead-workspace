# Real pilot preparation — not executed

The offline P5 rehearsal validates functional connections. The following real-data trial still
requires agreement with the project team and CGS; no fields below imply consent or completed work.
Do not use the synthetic demo percentages as a business baseline or acceptance target.

## Agree the trial

| Decision | To record before execution |
| --- | --- |
| Trial owner and CGS reviewer | Names / roles: pending |
| Approved problem and capability | Direction, geography, company cohort and version: pending |
| Allowed sources and data handling | Public sources, storage, retention and sharing: pending |
| Sample and two-round protocol | Small company list, distinct teams/problems, comparison design: pending |
| Contact relevance | What makes a contact usable; who verifies role and relationship: pending |
| Human decisions | Who reviews research, accepts cases and approves direction changes: pending |
| API accounts and spending | Client-approved providers/models, cost cap and stop rule: pending |
| Success definitions | Functional gates plus agreed usefulness/time measurements: pending |
| Client sign-off | Named decision-maker, date and decision: pending |

A two-company repeat like the offline rehearsal can verify plumbing but cannot establish
lead-quality improvement. Agree a suitable sample and comparison with the reviewer. If the
second round changes companies as well as direction, record that confound explicitly.
No automatic outreach is part of this trial; any contact happens through a separately authorized
human process and is then recorded in the workspace.

## Run in the main workspace

1. Back up both main databases. Keep the offline demo as an independent reference.
2. Enter authorized keys/models privately in the server environment. Do not paste keys into
   chat, code, test fixtures or reports. Check configured status without displaying secret values.
3. Verify account connectivity with a bounded authorized action. Record the provider, model,
   sanitized result, usage and date. A successful synthetic adapter test is not this check.
4. Approve the actual direction and data handling before replacing mock settings. Record the
   approval basis honestly; editing a label is not client approval.
5. Run round 1 through the real worker. Verify company identity, source URL/date, exact quote,
   uncertainty and contact suitability. Separate retrieval failures from irrelevant findings.
6. Review each opportunity with a reason and scope. Measure actual review time; retain unknowns.
   Record whether a next action could realistically use the brief/contact.
7. Explicitly accept, return or reject handoffs. Record relationship check, owner and next action.
   Public research still cannot populate confirmed qualification evidence by itself.
8. Analyze eligible feedback, inspect the proposed diff and approve/reject it as a named human.
9. Run round 2 with the approved version. Confirm it reached queries/prompts; assess results
   independently rather than presuming the update was an improvement.
10. Export a cleansed comparison and record reviewer acceptance, issues and the next decision.

## Minimum observation sheet

Keep one row per reviewed opportunity with company/team, task/opportunity IDs, round, direction
version, provider/model, signal and source/date, fact-versus-hypothesis check, contact role/source,
known relationship, decision/reason/scope, source-support check, actual review minutes or unknown,
receiving decision, owner, next action/due date, cost/usage and a short usefulness explanation.
Record any manually authorized outreach/reply separately, with dates and actual outcomes.

Report counts and denominators beside rates. Use the latest review per opportunity for the
dashboard and show all revisions separately for audit. Keep synthetic and real cohorts separate
in the evaluation; the current UI dashboard includes all versions and synthetic records.
Compare timing against a measured manual baseline. A tiny sample or a courtesy reply cannot
support a commercial conversion or model-learning claim.

Record the result as accepted, accepted with conditions, or not accepted by the named CGS
reviewer. Until that happens, client acceptance and business value remain unverified.
